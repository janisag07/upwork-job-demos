Email automation & drip campaign platform

An operator console for durable email drip sequences

This is the operator view of a self-hosted sending platform: a subscriber enters a sequence, jobs sit in a durable Redis/Celery queue until their scheduled time, a provider (SES, SendGrid, or Mailgun) sends the message, and delivery/bounce/unsubscribe webhooks feed back into contact state — with idempotency keys and retry/backoff so nothing silently duplicates or gets lost.

Durable queue monitor

Every send is a Celery task with a UUID idempotency key, stored in Postgres before the provider API is called. Retries use exponential backoff; jobs that exhaust retries land in a dead-letter state for manual review rather than failing silently.

Contact state & suppression

A contact that bounces or unsubscribes is marked suppressed and every one of their pending queue jobs is cancelled — suppression is enforced centrally, not per-sequence.

Provider webhook event stream

Each webhook payload carries a provider event ID. Before touching contact state, the worker checks whether that ID has already been processed — providers routinely redeliver the same event, and without this check a single bounce could be recorded twice.

Architecture

The moving parts, in the order a message travels through them.

01

FastAPI

Auth, validation, REST endpoints for contacts, sequences, and admin actions.

02

PostgreSQL

Source of truth: contacts, tags, custom fields, sequence steps, jobs, events.

03

Redis + Celery

Durable delayed jobs, beat schedule, retry/backoff, dead-letter handling.

04

Provider + webhooks

SES / SendGrid / Mailgun adapters behind one interface; signed webhook intake.

05

Docker Compose

api, worker, beat, redis, postgres, nginx — one command to run the stack.

Idempotency: every scheduled send carries a UUID idempotency key written to Postgres before the Celery task calls the provider API, so a retried task can never cause a duplicate send. Suppression: the worker checks contact status immediately before sending, not only at enrollment time, so a bounce recorded mid-sequence stops every later step.

Architecture & data model

  • FastAPI scaffolding and contact CRUD
  • Docker Compose skeleton (api, worker, redis, postgres)
Acceptance criteriadocker compose up boots every service; contact CRUD endpoints pass their tests; schema reviewed against the required custom fields and tags.
Milestone 2

Sending engine & webhooks

  • Celery beat schedule for delayed sequence steps
  • Provider adapter interface (SES / SendGrid / Mailgun)
  • Signed webhook intake, idempotency enforcement, dead-letter after max retries

Operator UI, deployment & handoff

  • Dashboard: contacts, queue, events, provider config
  • Production Compose profile, operator login
  • Automated tests, README runbook, handoff walkthrough
Acceptance criteriatest suite passes in CI; production compose profile deploys behind Nginx/TLS; client can operate the dashboard from the README alone.
